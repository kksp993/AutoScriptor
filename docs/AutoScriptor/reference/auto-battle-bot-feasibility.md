# AutoScriptor 自动战斗 Bot 可行性调研

> 调研日期：2026-10-21\
> 调研范围：当前仓库源码、测试、`docs/AutoScriptor/` 文档和相关 git 历史。\
> 调研方式：先阅读并遵守 `docs/agents/project-rules.md`；本次没有联网、没有启动模拟器、没有做在线截图/OCR，也没有修改产品代码。\
> 证据约定：下文把仓库中明确存在的行为称为“仓库事实”，把基于这些事实的工程判断称为“评估”；无法由仓库确认的事项会单独列出。

## 1. 结论摘要

### 1.1 总结判断

如果目标是**当前仓库已经覆盖的游戏和 MuMu 设备上的单一副本、固定战斗流程**，难度是**低到中等**：设备控制、截图、模板/OCR 识别、后台监听、战斗循环外壳、任务注册、调度、重试、取消和错误归档已经存在，可以直接复用，主要工作是补齐该副本的页面目标、战斗流程和验证样本。

如果目标是**一个副本内能够根据页面状态切换阶段的有限状态机 Bot**，难度是**中等**：已有 `battle_loop()`、`BattlePlan`、`bg` 信号和人工接管语义，但状态模型目前主要散落在各任务的布尔信号、回调和固定步骤里，还没有一个面向通用战斗的、可复用且可持久化的状态机层。

如果目标是**依靠视觉实时观察血条、目标、技能状态、危险区域并动态调整操作的闭环 Bot**，难度是**中到高，偏高**：历史基准显示 `screenshot_region()` 与 Nemu IPC 多指输入具备低延迟循环的基础，但不能据此认定完整战斗闭环已经达到要求；仓库也没有通用的战斗视觉状态提取、目标跟踪、技能/资源估计、时间同步、置信度融合或闭环策略模块。这部分不是简单地把现有 `click()` 串起来。

如果目标是**跨场景、跨职业、能自行理解未知战斗并规划策略的通用智能战斗 Agent**，难度是**极高/研究项目级别**，不适合当作当前 AutoScriptor 的直接 MVP。仓库没有通用战斗世界模型、策略搜索、行为记忆、奖励/评估闭环或面向游戏状态的智能推理运行时；可见的 OpenAI 多智能体文档也明确把示例限定在任务规划、审查和文档场景，不是战斗执行能力。

### 1.2 最重要的边界

- 当前仓库是“框架层 + 当前游戏业务层 + 编排层”的组合。`AutoScriptor/` 单独是可安装的设备/识别/脚本框架，不包含游戏业务、内置任务和 UI 素材；当前游戏战斗能力主要在 `ZmxyOL/`、`tasks/` 和 `data/character/`。
- 现有战斗实现的强项是**确定性流程自动化**：按已知位置、已知按钮、已知技能顺序、已知退出条件运行，并在失败时重试或交给人工。
- 现有实现不是“通用打怪器”：它没有从任意画面发现敌人、判断敌方威胁、选择目标或学习新战斗机制的能力。
- 最小可行路线应是“单副本固定流程 → 单副本有限状态机 → 单一视觉机制闭环”，而不是一开始接入通用大模型或追求跨游戏。

## 2. 依据和精确文件路径

### 2.1 设备控制、截图和实时输入

- `AutoScriptor/core/api.py`
  - `init()` / `ensure_app_running()`：显式建立设备会话，等待 MuMu、ADB 和 Android 就绪，并按参数决定是否拉起 App。
  - `screenshot_region()`：只取 ROI，适合高频检测；`finger_down()`、`finger_move()`、`finger_up()`、`multi_finger_down()`、`release_all_fingers()`：公开实时触控 API。
  - `replay()`：按时间戳、归一化坐标和 1~10 号手指回放固定触控事件。
  - `click()` / `swipe()` / `swipe_precise()`：普通定位后操作，以及固定起止点的精确滑动。
- `AutoScriptor/core/control.py`
  - `MixControl` 默认使用 Nemu IPC；截图始终从 Nemu IPC 获取。
  - Nemu 输入失败时，单次运行自动回退到 ADB，并记录错误；`switch_to_nemu()` 是重新启用快速路径的显式入口。
  - `screenshot_region()`、编号手指 API 与普通点击/滑动分开，允许实时触控和截图并发。
- `AutoScriptor/control/NemuIpc/device/method/nemu_ipc.py`
  - `NemuIpcImpl.screenshot()` 使用复用缓冲；`NemuIpc.screenshot_region_nemu_ipc()` 只转换 ROI。
  - `finger_touch_down()` / `finger_touch_up()` 是 MuMu IPC 原生编号手指通道；重复 down 表示移动。
  - `swipe_precise_nemu_ipc()` 提供固定直线和时长的触控轨迹。
  - `NemuIpcImpl.io_lock` 只保护复用截图缓冲；复合手势使用 `_ipc_lock`；编号手指输入不等待截图锁。
- `AutoScriptor/core/runtime_context.py`
  - `RuntimeContext.ensure_device_session()`、`refresh()`、`shutdown()` 统一管理设备会话生命周期，避免任务长期持有失效的 `mixctrl/mumu` 快照。
- `AutoScriptor/control/MumuAdaptor/device_facade.py`
  - 提供 ADB 设备就绪、App 状态、点击/滑动/输入等稳定兜底路径。
- `docs/AutoScriptor/reference/API.md`
  - 记录 1280x720 横屏绝对像素合同、ROI、多指、回放和任务 API。
- `docs/AutoScriptor/reference/fast-path.md`
  - 记录当前快速路径和 30Hz ROI 检测的历史实测：文档给出约 2~3ms 级截图/ROI 数据通路和约 30Hz 的简单检测闭环，但这是历史验证材料，不等于本次在线复验。
- `docs/AutoScriptor/reference/mumu-realtime-control-research.md`
  - 记录 MuMu IPC、多指输入、ROI 处理和实时闭环的历史调研与实测边界；文档同时明确版本差异和游戏内输入有效性仍需实机验证。

相关测试：

- `test/device/test_nemu_ipc_fast_path.py`：ROI 方向/边界、多指转发、手指释放、点击时长和 Nemu→ADB 回退。
- `test/device/test_nemu_ipc_concurrency.py`：截图与输入可并发、截图之间串行、编号手指不等待活动截图。
- `test/runtime/test_replay_events.py`：坐标换算、双指同刻事件、方向检查、取消和异常清理。

- `test/device/test_nemu_ipc_capture_retry.py`：分辨率变化时的正常重采与真实 IPC 故障分级。

### 2.2 OCR、模板、颜色和识别诊断

- `AutoScriptor/core/targets.py`
  - `T()`、`I()`、`B()` 分别封装文字、图片和坐标区域目标，目标可以携带搜索区域与颜色约束。
- `AutoScriptor/core/api.py`
  - `locate()` 支持单目标、tuple OR 和 list AND；`match()` 返回命中目标、路径和 Box；`extract_info()` 支持文本、已登记图片和混合识别，并可以固定同一截图帧。
- `AutoScriptor/recognition/locate.py`
  - 图片目标使用 OpenCV 模板匹配和有限尺度尝试；文字目标走 OCR；`get_box_color()` 提供颜色分类；多个目标可以批量定位。
- `AutoScriptor/recognition/ocr_rec.py`
  - 使用 PP-OCR 管线、线程局部引擎和短时缓存；`_frame_fingerprint()` 对完整图像内容做摘要，避免共享背景上的文字变化复用错误 OCR 结果。
- `AutoScriptor/recognition/ocr_engine.py`
  - 负责 PP-OCRv6 模型 profile、CPU/GPU 运行时校验和 PaddleOCR 结果归一化。
- `AutoScriptor/utils/ui_map.py`
  - 从 `ZmxyOL/assets/config/ui_map.csv` 加载文字、模板图片和默认区域；资产根不存在时框架可启动，但按 key 的游戏目标不可用。
- `AutoScriptor/logging/recognition_trace.py`、`AutoScriptor/logging/log_archiver.py`
  - 保存有限的识别摘要、帧来源、结果形状、动作历史和失败截图，便于定位“识别错了”与“输入没发出”的区别。
- `docs/AutoScriptor/reference/API.md`、`docs/AutoScriptor/reference/ocr-model-experiment.md`
  - 说明 OCR 语义和业务语义要分离；OCR 配置按进程启动快照生效，模型/设备变化需要重启。

## 3. 四个层级的难度评估

### 3.1 固定脚本：低到中等

**定义**：已知副本、已知分辨率、已知入口和按钮，使用固定的导航、技能、移动和结束条件；遇到未知页面就停止或交给人工。

**为什么可行**：

- 任务可以直接通过 `@register_task` 接入，参数可以由 WebUI 保存和恢复。
- `ensure_in()`、`T/I/B`、`click()`、`extract_info()`、`h.battle_loop()`、`h.way_to_exit()` 和 `bg.scope()` 已经构成完整的脚本执行积木。
- 当前战斗任务已经证明了“进入副本 → 选择难度/次数 → 固定连招 → 识别结束/失败 → 奖励/离场”的路径可以表达。

**主要缺口**：该副本的 UI map、模板、文字区域、职业连招和成功/失败后置条件仍需逐项制作；固定坐标只对符合 1280x720 横屏合同的设备可靠。

**判断**：做一个单一副本的安全 debug 任务是最现实的第一步；不要把“函数返回”当成功，必须验证页面状态或业务进度。

### 3.2 有限状态机：中等

**定义**：至少有 `进入`、`准备`、`战斗`、`胜利`、`失败`、`恢复`、`人工接管` 等状态，每个状态有进入条件、动作、超时、退出条件和重试上限。

**现有基础**：

- `battle_loop()` 已经是固定外壳，提供超时、取消、暂停和 `TRY_EXIT`。
- `BackgroundMonitor` 提供作用域、优先级、节流、并发回调和线程安全信号。
- `kunlunshan.py` 已经采用“回调只发信号、主线程在安全边界恢复”的思路。
- 调度器和任务管理器已经提供更高层的 retry、progress、人工接管和取消语义。

**主要缺口**：

- 没有通用的战斗状态对象、事件枚举、状态转移表和状态持久化；各任务仍大量使用局部字符串/布尔信号和固定步骤。
- 没有统一的动作后置条件检查器；点击成功只表示输入发送，不表示渲染或业务状态完成。
- 没有通用的“未知页面/低置信度”策略，容易在识别错时继续执行下一步。

**判断**：这是推荐的第二阶段。它可以显著降低无限循环、旧画面误判和错误重试风险，但应先在一个副本内收敛，不要一开始抽象成跨游戏框架。

### 3.3 视觉闭环：中到高，偏高

**定义**：持续观察 ROI，估计战斗状态，决定按住/松开/点击/等待，并在下一帧确认反馈；操作不是预先固定的时间序列。

**现有基础**：

- `screenshot_region()`、复用缓冲和 Nemu IPC 并发语义可以支撑高频 ROI 采集。
- 模板、文字、颜色、数字提取和固定帧输入已经存在。
- `finger_*` 可以表达持续按住/松开；`fast-path.md` 明确推荐只在状态翻转时发送边沿。

**主要缺口**：

- 没有当前游戏的玩家/敌人血条、目标框、技能冷却、危险区、动画阶段或可攻击窗口识别器。
- 没有通用的时序滤波、目标跟踪、遮挡处理、置信度融合、动作延迟补偿和丢帧处理。
- OCR 不适合作为 30~60Hz 热路径；仓库文档建议颜色/扫描线/简单视觉检测，但对应的通用战斗检测模块并不存在。
- 没有受隐私约束的、当前战斗 HUD 的固定帧基准。`test/fixtures/recognition_baselines/manifest.json` 目前为空，README 也明确说真实游戏基准尚待整理。

**判断**：如果只做一个简单的单机制闭环（例如一个 ROI 内的颜色/位置反馈），可以在固定脚本和 FSM 之后推进；如果要求完整战斗视觉理解，工程量会快速超过现有任务脚本层。

### 3.4 通用智能战斗：极高/研究级

**目标含义**：面对未知场景，自行理解战斗状态、选择目标和策略、适配职业/装备/敌人变化，并能长期稳定运行。

**仓库现状**：

- `Hero`/`BattlePlan` 是可扩展的规则 DSL，不是学习型策略系统。
- `ZmxyOL/battle` 的选择、难度、奖励和恢复逻辑都是当前游戏的显式业务代码。
- `docs/AutoScriptor/reference/openai-multi-agents.md` 描述的多智能体示例定位是任务规划、审查和文档；当前 checkout 中也没有可作为战斗运行时的 `examples/openai_multi_agents.py`。
- 没有训练数据、离线模拟器、战斗状态标注、策略评估集、回放评分器或安全的探索机制。

**判断**：这不应被包装成“加一个通用 Agent 就完成”。若未来要做，应先建立离线回放/仿真和人工接管边界，再考虑模型，只在受限的、可解释的动作集合内逐步扩展。

## 4. 当前可复用能力

1. **设备会话和生命周期**：MuMu 启停、ADB 就绪检查、App 拉起/关闭、Nemu IPC 连接释放和运行态同步。
2. **低延迟截图/输入**：全帧截图、ROI 截图、复用缓冲、固定精度滑动、多指按住/移动/抬起和触控回放。
3. **识别原语**：OpenCV 模板、OCR 文本、数字提取、颜色判断、注册 UI map、单帧批量识别和识别追踪。
4. **后台观察**：`bg.scope()`、节流、优先级、并发回调、事件历史和 `BG_SIGNALS`；适合把“战斗结束/失败/弹窗/前进”从主循环中解耦。
5. **战斗外壳**：`Hero.battle_loop()`、`BattlePlan` 的 first/at/every/combo、职业注册和 flow 选择。
6. **当前游戏业务流程**：导航到环境/位置、固定副本表、奖励/抽牌/先锋处理、出口搜索、多轮副本恢复和职业连招。
7. **任务编排**：注册、参数表格、任务排序、调度窗口、跨角色队列、重试轮、进度、人工接管、取消和热重载。
8. **排障与验收基础设施**：debug 截图、运行期帧、任务录屏、动作历史、识别 trace、错误归档、固定帧模板基准和大量 fake-control 单元测试。
9. **安全的失败语义**：`RequestHumanTakeover`、`TaskRequireReTry`、协作式取消和 `release_all_fingers()` 为“识别不确定时停下来”提供了现成接口。

## 5. 主要缺口

### 5.1 战斗感知缺口

- 没有通用的敌人/目标/玩家状态模型。
- 没有血条、目标选择、技能可用性、资源、危险区和动画阶段的统一识别器。
- 当前 `T/I/B` 能回答“某个已知目标是否出现”，不能单独回答“现在应该攻击谁、为什么”。
- 现有 OCR 和模板识别依赖固定区域、固定素材和当前 UI；对缩放、遮挡、特效、网络加载和 UI 改版的鲁棒性需要单独验证。

### 5.2 决策与状态缺口

- 没有通用 FSM、策略层或动作后置条件框架。
- 现有信号是线程安全的，但业务信号、页面目标、主线程动作和回调副作用仍需由每个任务自行协调。
- 没有战斗中断后从“当前战斗阶段”恢复的持久 checkpoint；任务级 progress 只能表达较粗的业务进度。

### 5.3 实时闭环缺口

- 目前有高速输入/截图通道，但没有通用检测算法、速度估计、预测、滞回或控制器实现。
- Nemu IPC 的版本、MuMu 发行版、横竖屏和后台保活行为存在差异；文档中的历史基准不能替代当前设备验收。
- 底层 `NemuIpcImpl.screenshot()` 返回复用 BGRA 缓冲的视图，直接调用它并跨帧保存时必须复制。公共全帧和 ROI 截图路径则在截图锁内通过 `cv2.cvtColor()` 生成独立 RGB 数组，不应把底层视图的覆盖风险泛化到这些公共返回值。截图调用耗时也不等于游戏的新帧间隔或动作生效延迟，仍需测量完整闭环。

### 5.4 数据和验证缺口

- 当前固定帧基准清单为空，没有当前战斗页面的隐私安全样本、期望 Box、OCR 文字和误报集。
- 当前测试多数是单元/fake-control/合成帧；没有本次调研范围内的在线战斗验收记录。
- 没有针对“点击后旧画面仍被读到”“失败界面与奖励界面相似”“重复挑战造成资源消耗”的系统级回放集。

### 5.5 安全和业务边界缺口

- 任务代码已经包含点券复活、重新挑战、商店购买等动作；通用 Bot 若复用这些流程，不能默认认为所有点击都是可逆的。
- 没有仓库内的游戏服务条款、账号处罚规则、反作弊接口说明或服务器状态 API。
- 只有 UI 观察和输入注入，没有服务端确认；“画面看起来胜利”不必然等于账号状态已经结算成功。
- `AutoScriptor` 运行数据和账号凭据有明确的落盘/解锁边界，但 Bot 的 debug 截图和录屏仍可能包含账号、角色或敏感页面，需要单独做脱敏和保留策略。

## 6. 推荐最小可行方案、里程碑与验证方式

### MVP-1：单副本固定流程（推荐的真正 MVP）

**范围**：只支持一个已知副本、一个已验证职业/连招、一个固定分辨率；入口和登录可以先由人工完成，Bot 只负责从“已进入挑战页”开始。

**实现形态**：

- 在 `tasks/` 或 `data/custom_task/` 写一个 debug 任务，复用 `ensure_in()`、`h.battle_loop()`、`bg.scope()` 和已有战斗流程。
- 所有关键动作都使用已登记模板/文字/明确 Box；每次点击后等待可观察的页面/区域变化，不用固定 sleep 代替业务完成条件。
- 只处理三个结果：明确成功、明确失败、未知/超时。未知直接 `RequestHumanTakeover`，不继续猜下一步。
- 默认关闭购买、点券复活、自动重新挑战和其他不可逆动作；`post_execution` 使用 `none`，首次运行保持 debug 现场。

**里程碑**：

1. 采集并审查一套隐私安全的入口、战斗中、胜利、失败和异常弹窗截图。
2. 为每个识别目标建立固定帧模板/OCR 基准，填充 `test/fixtures/recognition_baselines/manifest.json`。
3. 先用 fake `mixctrl` 和固定帧测试正常路径、旧画面、缺目标、错误弹窗和超时。
4. 在测试账号/非生产角色上进行人工看护的在线运行，验证停止按钮、失败后释放触控、错误归档和无资源误操作。
5. 连续完成一组有界的重复运行后，才允许接入调度器；调度接入仍应保留最大运行时长和 retry 上限。

**验收标准**：成功必须有明确的结算/回到地图/任务进度证据；失败必须留有截图和状态；未知画面不点击；取消后无手指残留；没有自动购买或点券消耗。

### MVP-2：单副本有限状态机

**建议状态**：`ENTER`、`READY`、`FIGHT`、`WIN`、`FAIL`、`RECOVER`、`MANUAL`。

**实现原则**：

- 状态转移写成显式表或小型类，不把所有逻辑继续堆到一个任务函数。
- 每个状态必须定义进入证据、允许动作、成功/失败/未知出口、超时和最大重试次数。
- 主线程负责导航、切图、重进和资源敏感动作；后台回调只发事件或置位标准信号。
- 用 `TaskManager` 的 retry/人工接管做任务级兜底，不在回调线程里递归重启整个业务流程。

**验证方式**：使用固定帧序列和 fake 控制器驱动每条转移；增加取消发生在每个状态的测试；增加“旧帧命中”“成功后仍看到旧按钮”“失败后奖励页误判”等回归样本。

### MVP-3：单一机制的视觉闭环

**范围**：只选一个明确的 ROI 和一个连续反馈机制，不尝试完整理解战斗。例如一个可以由颜色/位置直接判断的按住/松开机制。这里不假定当前游戏存在某种具体机制，实际对象必须由在线截图确认。

**实现原则**：

- 业务识别/策略放在 `ZmxyOL` 或任务层，通用 `AutoScriptor` 只提供截图和输入原语。
- 热路径使用 `screenshot_region()` 和颜色/轮廓/扫描线等轻量检测，避免全帧 OCR。
- 只在状态翻转时发送 `finger_down`/`finger_up`；循环、异常、取消和超时都在 `finally` 中释放本次手指。
- 先记录原始 ROI、检测结果、决策和输入边沿，再优化频率；不要先追求 60Hz 再补可观测性。

**验证方式**：离线逐帧回放、合成边界帧、丢检测/遮挡/延迟注入测试，再做低频在线试跑；只有在失败时安全松手且不影响其他任务后，才提高频率。

### MVP-4：受限的自适应战斗

只在 MVP-1~3 稳定后增加少量可解释分支，例如“目标 A 不可用则选择目标 B”“技能未就绪则等待”“检测到明确危险则退出当前轮”。每增加一个分支都要增加对应固定帧、回放和在线验收样本。不要把“自适应”解释为未知场景自由探索。

### 不建议作为 MVP 的方向

- 直接接入 VLM/通用 Agent，让模型自由点击生产账号。
- 先做跨游戏抽象，再回头验证一个副本。
- 用 OCR 全帧轮询替代明确 ROI 和模板/颜色检测。
- 通过模拟随机点击、伪装时序或其他方式规避检测。仓库没有证据表明这些方式安全，也不应把它们作为设计目标。

## 7. 失败模式、账号/服务条款/检测风险与安全边界

### 7.1 主要技术失败模式

1. **旧帧/渲染未完成**：`click()` 返回只表示输入已发出；立即读取可能仍是上一帧。必须等待名称、模板、区域值或加载状态等可观察变化。
2. **坐标和方向不匹配**：内置素材是 1280x720 横屏绝对像素；分辨率、方向或 UI 缩放改变会造成识别漏检和误点击。
3. **OCR/模板误识别**：文字子串可能在提示语中重复，模板可能被特效、缩放、遮挡或主题变化破坏；高风险动作不能只靠一次命中。
4. **Nemu IPC 版本/连接异常**：输入可能回退到 ADB，实时闭环的时序和频率随之失效；截图故障、分辨率变化和模拟器退出需要分开处理。
5. **后台回调与主线程竞态**：回调若直接切图、重进或修改轮次，可能与 `battle_loop()` 同时操作设备；当前文档要求回调只置位信号，主线程在安全边界收尾。
6. **弹窗遮挡**：MuMu 系统弹窗会吞掉后续所有点击；如果没有先识别并关闭，任务可能表现为无关页面超时。
7. **重试放大副作用**：成功结算但客户端没有及时刷新时，重试可能重复挑战、购买或消耗门票；重试必须绑定明确的业务状态和资源上限。
8. **无限循环/手指残留**：实时循环、出口搜索和战斗监听都必须有超时、取消和清理；任何异常路径都要释放手指和后台监听。

### 7.2 账号、服务条款和检测风险

- 当前仓库没有当前游戏的 EULA/服务条款、反作弊说明、封禁判据或服务端 Bot 检测接口，因此不能从仓库确认“是否允许自动战斗”“哪些行为会触发处罚”或“某种输入通道是否可被识别”。
- 从一般工程和运营角度，自动登录、连续重复输入、无人值守战斗、点券/购买操作和跨角色批量执行都可能触发账号、服务或经济系统风险；Nemu IPC 的低延迟或“拟人化”轨迹不等于合规，也不等于不可检测。
- 本报告不建议、也不支持绕过反作弊、隐藏自动化、修改客户端/内存、注入网络协议或伪造服务端结果。若当前游戏条款不允许 Bot，应停止在生产账号上部署。

### 7.3 建议的安全边界

- 先使用专门测试账号/角色，人工看护首轮运行；未确认条款前不要用于生产账号或有价值角色。
- 默认只允许导航、战斗和明确的成功/失败检测；购买、点券复活、交易、删除、领奖确认和重新挑战全部设为显式人工确认或关闭。
- 对每个副本设置最大运行时长、最大点击/重试/恢复次数、资源消耗上限；超限进入 `MANUAL`，不继续点击。
- 识别置信度不足、画面不在白名单、出现未登记文字或弹窗时 fail-closed：停止并抛 `RequestHumanTakeover`。
- 使用 `debug=True`、运行期截图/录屏和错误归档做受控验收；确认截图不会包含凭据后再扩大保留范围。不要把账号密码、token 或真实账号文件写入报告、测试夹具或 Git。
- 所有实时循环在 `finally` 中释放本次手指；停止按钮、任务取消、设备断开和异常都必须走同一清理路径。

## 8. 明确无法仅从仓库确认的结论

以下事项本报告不做确定性结论：

1. 当前游戏的实际战斗机制、敌人行为、目标优先级、技能数值、伤害判定、服务端结算和网络同步方式。仓库中的副本名、按钮文字和脚本分支只能证明脚本作者曾按这些 UI 编写流程，不能推出完整游戏规则。
2. 当前机器/当前 MuMu 版本在真实游戏画面内的 Nemu 输入稳定性、坐标正确性、后台保活行为和高频切换上限。`fast-path.md` 与 `mumu-realtime-control-research.md` 的数据有明确历史环境和日期，不能替代本次在线复验。
3. 当前战斗 HUD 的 OCR/模板准确率、误报率、真实延迟和特效/遮挡下的鲁棒性。仓库有通用 OCR 测试，但 `test/fixtures/recognition_baselines/manifest.json` 目前为空，没有经审查的战斗样本集。
4. 任何账号是否会被封禁、限流、标记或要求人工验证。仓库没有当前游戏服务条款、风控规则或反作弊证据。
5. 一个通用模型是否能在该游戏中稳定产生有效策略。仓库没有训练集、离线战斗模拟器、标注状态集或策略评估基准。
6. 当前工作树相对某个干净提交的全部产品差异。调研开始前已存在其他 staged/unstaged 变更；本次没有修改或回退它们，因此结论是对当前工作树的研究，不是对某个干净发布版本的审计。

## 9. 最终建议

把目标定义为：**“一个副本、一个职业、一个分辨率、固定入口、失败即人工接管的安全战斗脚本”**。先用现有 `Hero`/`BattlePlan`/`bg`/任务调度能力完成可重复的固定流程，再用显式 FSM 解决阶段和恢复，最后只针对一个经过截图和回放验证的视觉机制做闭环。这样可以最大化复用当前仓库已有能力，同时把真正的风险集中在可测量的识别、同步和失败边界上，而不是提前承担通用智能战斗的不可控复杂度。
