# AutoScriptor Agent Rules

This file is the shared project rule source for Codex, Claude Code, Cursor, and other coding agents. Tool-specific entry files should point here instead of maintaining separate rule copies.

## Entry Points

- Codex: `AGENTS.md`
- Claude Code: `CLAUDE.md`
- Cursor: `.cursor/rules/00-shared-project-rules.mdc`
- Optional local skills may point here, but `.codex/` and `.claude/` are git-ignored and must not become the durable source of truth.

When rules conflict, prefer the most specific project rule, then the tool's system/developer instruction, then the user's latest instruction.

## Core Workflow

Use this workflow for bug fixes, anomalies, regressions, and project improvements:

1. Record failures or stale evidence first, then fix and rerun.
2. Locate the failing layer: source startup, WebUI/frontend, backend service, scheduler, AutoScriptor core execution, task authoring, recognition/OCR, config/account/status, or update state.
3. Trace the lifecycle end to end: initialization, registration, runtime state, persistence, reload, retry/error path, cleanup, API payload, and UI projection.
4. Check local evidence first: `rg`, nearby tests, docs, and git history for touched files when the area is subtle or recently changed.
5. Identify the violated assumption before editing.
6. Make the smallest targeted fix using existing APIs and local patterns. Avoid new abstractions unless they remove real complexity.
7. Validate with focused tests or a reproducible probe. Check normal path, edge path, and lifecycle side effects.
8. Audit `docs/AutoScriptor/` for every behavior/API/lifecycle/state change. Use `docs/AutoScriptor/README.md` as the map, check every affected functional domain, then update shared agent rules or skill references when the change teaches a reusable rule or workflow.

Avoid permanent state traps such as "once marked, never runs again" unless explicitly intended.
For exception handling, fail precisely in install/run/update/config/security/path code. Runtime device/OCR/task boundaries may catch and record operational failures, and error archive/log cleanup may protect the original error, but do not add broad fallback paths that hide programming errors or resurrect removed product surfaces.
WebUI dynamic option/status probes must return visible API errors when imports, enum classes, config reads, or Paddle/OCR probes fail; do not synthesize empty lists, `false`, `0`, or `unknown` to make panels appear healthy.
WebUI settings fields must be both editable and actually persisted. Do not lock a user-facing config field with a hard `:disabled="true"` unless the backend truly owns the value, and do not leave an `emits` event without a reachable trigger: a `settings-change` handler with no button, watcher, or debounce path silently drops every edit while the page still claims it saves. Settings autosave must compare `app/emulator/ocr/scheduler` snapshots and only emit when `config_version` is unchanged (a user edit) and the snapshot differs from the baseline, so the post-save server refresh only rebaselines instead of re-triggering a save loop; changes made while a request is in flight must be re-queued so the UI and `data/config.json` converge. Validate at the field level and pause autosave on invalid input rather than posting a value that the backend will reject or normalize. When a field has both a derived default and manual entry, keep the derivation only for empty/placeholder/`:0` values and preserve explicit user values.

## Source Workflow Discipline

The `src` branch is source-run only. The durable user paths are:

- Install source dependencies: `scripts\install.bat`.
- Desktop shell: `scripts\run.bat electron` or root `start.bat`.
- Backend WebUI: `scripts\run.bat webui`, root `webui.bat`, or `.venv\Scripts\python.exe -X utf8 backend\webui\gui.py`.
- Static WebUI assets: `backend/webui/static/`.
- Source updater: `scripts\update.bat` for manual Git updates; `/api/update/status`, `/api/update/check`, `/api/update/run` for WebUI updates.

Do not restore deleted command-menu shells, desktop distribution builders, setup wizards, binary delta services, or extra update channels unless the user explicitly asks for that product surface again.
Do not restore Nuitka/compiled-runtime bootstraps, runtime import smoke probes, MuMu packaged-runtime probes, generated task manifests, or package/frozen data-root fallbacks unless the user explicitly asks for those product surfaces again.

For source startup:

- Keep `start.bat`, `webui.bat`, `scripts/install.*`, `scripts/run.*`, `scripts/update.*` and `frontend/electron/main.js` aligned with source execution. `start.bat` and `webui.bat` are the two root shortcuts and only forward to `scripts\run.bat`; there is no separate launcher or Python bootstrap script.
- Source install uses winget for Git/Node.js LTS/uv, then `uv venv --python 3.10.15` for `.venv`, then `uv pip install`, then `npm install` inside `frontend/electron`.
- Source OCR install keeps shared dependencies in `requirements.txt` and selects exactly one Paddle
  runtime from `requirements-cpu.txt` or `requirements-gpu.txt`; `paddlepaddle` and
  `paddlepaddle-gpu` must never coexist in `.venv`. Keep the installed variant aligned with
  `data/config.json -> ocr.use_gpu`. OCR device/model settings are process-start snapshots shared by
  global, thread-local, and digit engines, so changes require reinstalling the matching variant when
  needed and restarting AutoScriptor. If GPU is configured without CUDA Paddle or an available CUDA
  device, fail visibly instead of silently falling back to CPU. Keep `setuptools<81` while the pinned
  legacy `adbutils` path still imports `pkg_resources`; source installation must verify both that
  version constraint and the `pkg_resources -> packaging.tags -> distutils.util -> adbutils ->
  uiautomator2` import chain after installing the Paddle variant.
- Keep `frontend/electron/package.json` focused on source Electron startup. Do not hide Python bootstrap or Git update work inside npm lifecycle hooks.
- Keep WebUI logs on native WebSocket `/ws/logs`; do not reintroduce SSE or Socket.IO assumptions.
- Source Git updater must disable itself outside a Git working tree or non-source runtime instead of pretending another update path exists. It must reject detached HEAD, check with a single explicit `git fetch origin main`, compare `HEAD` against `origin/main` with ahead/behind counts, fast-forward only the current checked-out branch from `origin/main`, and surface the exact git stderr/timeout/start failure through WebUI status instead of collapsing failures to empty output, generic messages, or slow retry loops.

After moving, renaming, or materially rewriting docs, run `rg` for stale paths and stale behavior claims across `docs/AutoScriptor`, `docs/agents`, README, `docs/AutoScriptor/INSTALL.md`, tests, and scripts.

## Editing Rules

- Do not revert unrelated user changes.
- There is no root `tools/` directory. Durable source-maintenance scripts belong in `scripts/`; reusable runtime helpers belong in package modules such as `AutoScriptor/utils` or `AutoScriptor/core`; one-off probes and personal experiments should stay untracked. Live screenshot/OCR checks run in-process against `AutoScriptor` and write their evidence under `<logs-root>/<topic>_<timestamp>/`; see `.cursor/skills/autoscriptor-live-check/SKILL.md`.
- Prefer package imports, for example `from AutoScriptor.core.box_grid import make_box_grid, indexof`.
- Keep OCR/recognition semantics separate from business semantics. Example: OCR returns `None` for unreadable empty badges; inventory logic may later map missing item to `0` or visible item without badge to `1`.
- Treat device input completion and UI rendering completion as separate events. When extracting data immediately after a click, wait for an observable target/region/value change before accepting the next frame; `ensure_not_empty` alone can accept a non-empty value from the previous frame. OCR frame caches must fingerprint complete image content rather than sparse sample pixels so labels on a shared background cannot reuse stale text.
- For task state/progress, do not treat "function returned" as "business succeeded" when observable completion state exists.
- Device recovery has one escalation ladder, owned by `TaskManager._try_recover_app()`: close and relaunch the app, restart ADB on the next attempt, and only after three consecutive recoveries where the app never reaches `running` restart the MuMu instance (`runtime_ctx.release_session()` -> `mumu.power.restart()` -> `runtime_ctx.refresh(launch_app=False)` -> relaunch the app). Keep a cooldown between MuMu restarts and clear the failure counter on a successful task, so an unattended broken session cannot become a restart storm. This counter is separate from task retry/attempt accounting.
- For character notifications, freeze identity/results before asynchronous delivery, merge retries by run id, and keep delivery failures out of game retry counters. Never infer Yuxu completion from a consumed ticket or report missing combat/activity measurements as zero. See `docs/AutoScriptor/operations/qq-notifications.md`.
- Optional QQ robot installation belongs to `scripts/install.bat qq` / `backend/core/qq_bot.py`, not game tasks or npm hooks. Verify the pinned official archive hash before extraction, keep credentials/login data out of Git, bind both management and OneBot HTTP to loopback, and transfer connection settings through the existing WebUI lifecycle transaction instead of rewriting a live config file. Preserve existing installs; never enable notifications or invent a recipient. After a successful game-account security-key verification, it is explicitly allowed to auto-start the already-installed local bot only when QQ notifications are already enabled and a cached login session exists; use the remembered/cached QQ account for quick login and never launch a first-time QR flow. NapCat v4.18.19 Node startup requires the upstream `NAPCAT_DISABLE_MULTI_PROCESS=1` switch because its fork branch passes unsupported `--no-sandbox` to Node.
- For the explicitly separate remote-computer deployment, use the self-contained `scripts/qq-robot-standalone/` PowerShell scripts, not the source installer or Python helper. Only this path binds OneBot to a user-specified private LAN/VPN IPv4 and creates a program/port/source-IP-scoped firewall rule; keep management loopback-only and refuse startup if the scoped rule is missing. Do not create firewall changes on the script computer during validation. Offline PowerShell firewall tests must verify every mocked command resolves to the test script before invoking it; a missing removal stub previously reached a nonexistent random rule (no rule was removed). Never copy runtime credentials/login data with distributable scripts.
- For battle/background control flags, use `BG_SIGNALS` constants instead of ad-hoc signal string literals. Treat `BG_SIGNALS.FAILED` (`"Failed"`) as the only failure state; the lowercase `"failed"` spelling is only a compatibility alias mapped by `BackgroundMonitor`, not a second signal to set separately. Set `BG_SIGNALS.TRY_EXIT` when the current `battle_loop()` must stop.
- Values a consumer reads with a hard subscript (for example `cfg["weekday"]` in the village daily tasks) must be guaranteed by whatever builds that mapping, never by the caller happening to save or reload first. `AutoConfig._refresh_flat_config()` is the only place `cfg._config` is assembled, so the runtime date block (`year`/`month`/`day`/`weekday`) is applied there and stays out of `_GLOBAL_KEYS`: a persisted calendar would survive a restart as a stale date. When adding a field that some code reads directly, put it in the view builder and prove it with a test that loads config without any intervening save.
- For task registration, `TaskRegistry` stores runtime data (function, registration order, parameter specs, doc/debug flags) keyed by display path, while `cfg["tasks"]` stores user configuration keyed by task **id**.
- A task has two names and they must not be conflated. `id` is the identity: it keys `cfg["tasks"]` and `task_ordering`, so user config and drag order survive a rename. `path` is the display location: it drives the WebUI tree, execution order, and parameter labels. `id` is the task's name (the file stem), so a new task declares nothing and **moving a task between folders never touches user data**; only renaming the file needs `@register_task(id="<old name>")` to pin the identity, and storage then keeps the old key while the tree shows the new location. Registering two tasks with the same id is an error and must fail loudly.
- The two key spaces meet in exactly one place, `retarget_ordering_overlay()`: the stored overlay is id-keyed, everything downstream (projection, WebUI payload, executor) speaks display paths. Do not invent a second translation point.
- `cfg["tasks"]` is a flat table, not a nested tree. The WebUI tree is assembled per request from display paths (`TaskTreeService.build_task_tree()`) and flattened back on save (`flatten_payload_tasks()`); nothing in storage depends on the tree's shape. `catalog.normalize_task_table()` rewrites a legacy nested table into the flat one at load, before the first `@register_task` runs.
- Task parameters have one definition: `tasks/task_params.py` derives a `ParamSpec` per parameter from the function signature, and the JSON default (`json_default()`), the WebUI form description (`describe()`), and execution decoding (`decode()`) all read that spec. Adding a parameter kind means adding a `ParamSpec` subclass, not branching in registration, the executor, or the frontend. Enum options travel inside `describe()`, so there is no separate option-lookup endpoint.
- When a task adds rows or columns to a `TableParam` default, the table spec merges those nested defaults into existing saved rows while preserving user values; replacing the whole table or leaving new cells absent makes upgrades unmanageable in WebUI.
- A task reload re-imports task scripts but keeps the modules that own process-wide objects: `tasks.task_register` (the registry singleton every reader holds), and the authoring plumbing (`task_params`, `task_state`, `time`). `tasks` itself and `tasks.battle_task_params` are rebuilt because the flow enum aggregates `@flow` registrations from character scripts. `ZmxyOL` is not purged: it owns cross-boundary types such as `TableParam`, and character scripts are refreshed by `reload_character_modules()`. `ZmxyOL.drop_cached_exports()` clears the lazily bound re-exports so a star-import serves the post-reload enum. `orchestrator/catalog.py` holds the kept-module list; `test/task_domain/test_task_reload_contract.py` pins it.
- The stale-entry prune refuses to run when the registry is empty. "No task is registered" means registration did not reach the registry being read, not that the saved table is stale, and pruning there deletes every entry. `normalize_task_table()` carries the same guard in the other direction: it never writes an empty table for a non-empty input.
- Built-in task order is the registration order, which is the sorted source path under `tasks/`. There is no per-task order parameter and no order file: user display/execution order belongs in global `task_ordering` under `data/config.json`, keyed by task id.
- WebUI task-tree saves and task-ordering saves must share one FIFO frontend commit sequence with payload snapshots frozen at enqueue time. Ordering responses are domain projections and must never replace `configData.tasks`; runtime polling must settle that commit sequence and request a full config refresh only when the response `config_version` is greater than the current version.
- Do not leave incomplete debug placeholders registered as built-in tasks. A script that hard-stops, prints internal tables, or leaves the real flow unreachable should be deleted or kept unregistered.
- Do not add task-file direct-run wrappers with broad `try/except`, `traceback.print_exc()`, `bg.stop()`, or `exit(0)`. Use WebUI direct run and the task's `debug` setting so scheduler logging, cancellation, retry, and cleanup semantics stay intact.
- Runtime failure evidence is produced during the run, never reconstructed after it. `debug` is a user-facing switch on the task config entry: the author declares a default on `@register_task`, the user can override it in the WebUI, and `is_task_debug_mode()` resolves both sources in one place, so the scheduler, executor and WebUI cannot disagree. `TaskManager` drives `tracer.set_run_capture()`; `MixControl.screenshot()` only forwards frames; the archiver moves the run's screenshots into the archive instead of re-snapshotting a screen that has already changed. Android `screenrecord` rejects `--time-limit` outside 1..180 and does not create missing parent directories, so task video rolls in <180s segments that each end on the device's own time limit, keeps only the newest few, and checks pulled MP4s for decodability before treating them as evidence.
- When editing Chinese task/source files on Windows, read and write UTF-8 explicitly and rerun a mojibake scan plus `py_compile`; do not trust terminal display alone.
- Rich console source links on Windows must use standard encoded file URIs such as `file:///D:/path/file.py`; preserve native paths in log records/files, and normalize only the terminal link target so Cursor does not resolve `file://D:\\...` as `\\`.
- Task scripts should prefer `from AutoScriptor import *` and `from ZmxyOL import *`; common task-facing utilities such as `logger` belong in those aggregate APIs instead of requiring internal module imports. Add generally useful operations to the aggregate APIs instead of importing internal `core_api` modules. Use `init(launch_app=False)` plus live `launch_app` / `close_app` / `go_home` wrappers for scripts operating a non-configured App. A portrait app task keeps explicit `frame_size=(720, 1280)` on its regions rather than calling `setFrameSize`, so it cannot leak a changed default to other work in the shared process.
- Shared task code lives in an underscore-prefixed module beside the tasks that use it, for example `tasks/其他任务/活动脚本/活动任务/_活动流程.py`, imported by full package path (`from tasks.其他任务.活动脚本.活动任务._活动流程 import run_activity`). The prefix marks it as a module rather than a task: it registers nothing and task discovery skips it.
- Use public `click_all(target)` to freeze and click every distinct match of one target on the current frame; `click(..., repeat=N)` repeats one matched position and must not be used as a substitute for multi-match clicking.
- Treat `LoginClient.HZ4399` as the 4399 Game Center login surface: after account submission it completes without waiting for the game's character-selection `进入游戏` page. Keep that client split centralized across authorization, password-login, and quick-login routes; only game clients select servers and characters.
- For account/character data, remember active character tasks and status are persisted in account JSON, then flattened through `cfg` at runtime.
- For paths, use `AutoScriptor.utils.paths`; source mode uses `data/config.json`, `data/accounts`, `data/custom_task`, `data/character`, and `logs`.
- WebUI Editor custom-code execution must stay aligned with task authoring APIs, including `AutoScriptor` core helpers plus public `ZmxyOL.nav.api.*` and `ZmxyOL.nav.envs.decorators.*` symbols. Editor-saved scripts are persisted under `get_custom_task_dir()` at the path the script name implies (`自定义任务/<目录...>/<名字>.py`), because a custom task's display path is its location; saving then reloads tasks through the lifecycle service so the WebUI task tree observes the new script.
- WebUI Editor coordinates use the current screenshot's native width and height. Raw remote clicks, generated code, execute-code, previews, and saved scripts must agree on those coordinates; for non-1280x720 T/I recognition regions, generate and preserve `.margin(frame_size=(width, height))` instead of silently clipping through the built-in landscape default.
- Do not delete MuMu dynamic adapter attributes or task-authoring helpers solely because `rg` cannot find direct callers. `BaseMumuControl.__getattr__`, `from AutoScriptor import *`, and user scripts can reach these APIs dynamically.
- Long-lived runtime modules must not keep imported `mixctrl`/`mumu` snapshots from `from AutoScriptor import *` or `from AutoScriptor import mixctrl`; read the current object from `runtime_ctx` or `AutoScriptor.core.api` at the call site.
- For config/account persistence, keep atomic same-directory replace and do not fall back to direct target-file writes after replace failure. Do not add unconditional `fsync` to WebUI interactions; low-RAM or antivirus-constrained Windows hosts can turn tiny JSON writes into multi-second stalls. Use `save_global_config()` for global-only settings such as deploy/notify/update/task_ordering so account JSON is not rewritten unnecessarily.
- Scheduler/runtime-owned writes to `data/config.json` or the current account JSON (task state, progress, `next_exec_time`) must not be mistaken for external hot-reload edits on the next scheduler tick. Rebaseline those handled config/account files while keeping `data/custom_task/` and `data/character/` script changes observable.
- WebUI stop controls are unified control paths: overview, scheduler, and task-list pages must reuse the overview `stop-dispatch` / `stopDispatch()` frontend action. `POST /api/stop` must preserve cooperative cancellation until workers exit while restoring scheduler state to pending, clearing consecutive-error and retry-exhaustion budgets, and ignoring post-cancel failures for error counting. Apply the returned lightweight runtime projection immediately and let background refresh or normal polling fetch `/api/runtime/snapshot`; do not synchronously wait for full task-tree/config snapshots in the click handler.
- Keep scheduler activation separate from execution occupancy. `SchedulerState.RUNNING` means automatic scheduling remains enabled; it must not by itself set runtime/frontend busy or block task-list/Editor actions. Scheduled pipelines, direct runs, Editor execute-code, and Editor remote click/swipe must share one execution gate: manual entrants may run while scheduling is enabled and idle, active scheduled execution returns a wait/retry conflict without requiring scheduler shutdown, and the scheduler blocks behind an already-started manual action then resumes with its activation state unchanged.
- WebUI task-list execution controls (run due tasks, run one task, and run from the selected task) must mark `/api/run` with `execution_source=task_list`. That source preserves the current game login cache and skips `_ensure_character_logged_in()` while keeping credential unlock, runtime guards, normal-task restart checks, retry, persistence, notification, and post-execution behavior unchanged. Scheduler, cross-character, default direct-run, and gift-code flows must retain their existing login checks; explicit `force_login` wins.
- Static runtime JSON/data assets belong under `data/assets/...` when they are needed at runtime; mutable generated caches belong under `logs/` via `get_logs_root()`. Do not treat `docs/refs/**`, `docs/*.json`, or third-party reference material as runtime payload.
- Optional OpenAI Agents SDK examples must stay outside the main source runtime, for example under `examples/`, unless the user explicitly asks to integrate OpenAI API calls into AutoScriptor. Do not add `openai` or `openai-agents` to `requirements.txt` for optional examples alone; document the opt-in setup instead.
- For source Electron startup, create the visible loading window before slow checks such as port cleanup or Python backend startup. Loading UI and `backend\webui\gui.py` must emit phase logs for Python process creation, WebUI import, worker start, and WebUI polling so first-run delays are observable. Do not change the Windows console code page from Electron; port cleanup failures must be logged visibly.
- For source Electron GPU/Chromium stalls, keep mitigation inside `frontend/electron/main.js` render-mode startup switches. Configure `AUTOSCRIPTOR_ELECTRON_RENDER_MODE` before `app.whenReady()`: default `software`, optional `d3d11`, or `default` for comparison. Do not use host power, process priority, thread priority, CPU affinity, or MuMu priority fallbacks for Electron stalls.
- For MuMu TCP ADB checks, remember `adb start-server` does not connect `127.0.0.1:<port>` devices. Device readiness probes should `adb disconnect <configured adb_addr>` then `adb connect <configured adb_addr>` and retry `get-state` before treating `device not found` or `offline` as a final failure; plain `connect` on an already-listed offline TCP serial often returns `already connected` without healing. NemuIpc screenshot success does not prove ADB is connected. A running MuMu process also does not prove ADB or Android is ready: every newly built device session must wait for the configured serial to report `device` and `sys.boot_completed=1` before launching the app or creating controls. Restart tasks must release stale runtime/NemuIpc state before restarting MuMu and rebuilding the session.
- After `MuMuManager launch` succeeds, treat it as command acceptance only. `Power.start()` must wait for the configured ADB device and Android boot completion before package resolution, App startup, or other Android-side checks.
- NemuIpc is two lanes, not one: `NemuIpcImpl.io_lock` protects only connect/disconnect/reconnect and the reused capture buffer, while `NemuIpc._ipc_lock` only serialises compound gestures (click/swipe/long-click) against each other. Screenshots and touch injection are proven to run concurrently on the same connection (measured zero errors at ~450fps capture + 50Hz injection), so do not reintroduce a cross-instance global lock, do not make input wait for an active screenshot, and do not wrap worker-thread capture in the caller's lock. The default input channel is Nemu IPC (`MixControl.mode="nemu"`); an IPC input failure (`NemuIpcError`/`RequestHumanTakeover`) falls back to ADB for the rest of the run with an explicit error log, and `switch_to_nemu()` re-arms the fast path. Do not paper over deterministic IPC contention with broader retries or fallback sleeps.
- Realtime closed loops (progress-bar style) use `screenshot_region` for ROI-only conversion plus numbered-finger edges (`finger_down`/`finger_up`/`multi_finger_down`), never a full-frame OCR loop; they must be edge-triggered and guard `release_all_fingers()` in `finally`. Numbered fingers (1..10) are a separate contact pool from the legacy single-contact click channel: verified on MuMu 5.30.1.3586 via the pointer-location overlay that a legacy click while a numbered finger is held does not release it, and `finger_touch_up` on unpressed fingers returns success and costs <1ms total for all 10.
- Source runtime must not change Windows power state, away mode, display keepalive, CPU affinity, process priority, thread priority, or MuMu process priority as a performance fallback. `AutoScriptor.utils.perf` has been removed; fix OCR frequency, screenshot reuse, ADB state, NemuIpc serialization, or task loops instead.
- Do not spread `interval=0.5` through task scripts just to get the default click-until polling cadence. `click(..., until=...)` owns that default; plain `click()` remains immediate unless the caller explicitly passes an interval.
- `Hero.way_to_exit()` uses `bg.scope()` to watch for exit signs while the main thread moves in phases: reach the far right, move left near the exit, register `战斗-离开标记` only after that positioning, pulse-search left, hold on the countdown `秒`, then micro-adjust right only if the hold did not complete. Use `mumu` for these exit long-press movements and switch back to `nemu` after each movement for recognition. Treat `还有`/`秒` as an exit-position marker, not a completion `until`; completion must be loading, home, draw-card, or another post-exit state. Do not reintroduce private detector threads, `fast_until`, OCR throttling, or list/AND special cases inside this method.
- For Heaven team dungeons, visible `抽牌` means the battle loop should stop. The `heaven_battle()` background scope must use `bg.interval(0.1)` so battle-end/draw-card/failure detection locates a fresh screenshot every 0.1 seconds instead of waiting on the default 1 second bg cadence. The battle-end callback sets `BG_SIGNALS.PAUSE_BATTLE` and `BG_SIGNALS.TRY_EXIT`; the failure callback sets canonical `BG_SIGNALS.FAILED` plus pause/exit before stopping the loop. Run `way_to_exit()`, draw-card cleanup, cancel-revive, and retry handling after `battle_loop()` returns on the main thread so callback exceptions cannot swallow the exit signal. When callers pass `exit_after_battle=False`, failure handling must return with `BG_SIGNALS.FAILED` left for the caller instead of recursively starting another challenge inside `heaven_battle()`.
- For latest boss dungeons that may trigger "混沌先锋", task scripts should pass `battle_task(check_pioneer=True)` and keep detection plus challenge/exit handling in the shared heaven battle procedure. When users need per-dungeon control, put a boolean such as `fight_pioneer` directly in each `TableParam` row and pass that decision to the shared procedure; do not pass source-dungeon names, recognize the previous dungeon from the pioneer screen, or store mutable module-global context. The normal post-battle return-home flow must finish first; only then open the short pioneer detection window, and always reset transient detection state during cleanup. Do not wrap the previous not-yet-home exit flow inside the pioneer watcher, and do not scatter one-off pioneer checks or auto-entry quickfixes through individual task scripts.
- For WebUI logs, use native WebSocket `/ws/logs`.
- For update work, keep the single source Git channel separate from manual dependency/bootstrap changes.
- For security scans, the exact 4399 public news pair `85rwm3janyyc` / `123456` is the only allowed real-looking plaintext credential exception. It is a public runtime dependency for 4399 news/forum proxying and must remain plaintext; do not remove it as a leak. Every other account, password, token, deploy secret, private key, and account JSON is sensitive.

## Validation

Use `.venv\Scripts\python.exe -X utf8` on Windows unless there is a clear reason not to. The suite is `unittest`-based; `test/README.md` documents the layout and how to run one package, file, or case. Prefer targeted runs plus `py_compile` while iterating, then a full `-m unittest discover -s test` before reporting done. New behavior gets a test file in the matching domain (`test/webui/`, `test/accounts/`, ...) rather than a throwaway probe, and any defect that only shows up at runtime (server startup, real requests, lifecycle ordering) should be pinned by one of those tests.

Tests must never write real runtime data. In-process saves from test processes are refused by `_refuse_test_process_write`; tests that exercise real save paths must redirect `cfg.CONFIG_PATH` and the account directory to a temp dir (`TestCfgSaveClean` pattern); and any test that spawns a Python subprocess importing the app must set `AUTOSCRIPTOR_DATA_DIR` to a temp dir, because the guard does not apply across process boundaries. The guard freezes the test-runner signal when `AutoScriptor.utils.app_config` is imported; never re-check `sys.modules` at write time, because the real runtime imports `unittest` indirectly through Paddle and would otherwise be misclassified as a test process and have all saves refused.
