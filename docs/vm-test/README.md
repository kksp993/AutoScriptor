# Windows 虚拟机用于安装与发行测试 — 调研说明

本文档对「能否在 Windows 虚拟机里做安装、首次运行、发行物验证」做**分工式**调研：按**场景**、**许可**、**技术限制**、**与本项目栈的匹配度**分别说明，便于你分配人力或选择环境。

---

## 0. 没有全新物理机时，怎么测「第一次安装」

现实情况往往是：几台常用电脑**早就装过依赖、改过 PATH、跑过旧版**，已经**不能代表**「用户第一次双击安装包」的环境；再买一台专门测安装，成本又高。可以这样理解问题与对策：

**目标澄清**：你要验证的不是「宇宙里每一台 PC 都能跑」，而是**在可重复、尽量干净的环境里**，安装包与首次运行逻辑**没有明显缺陷**；再辅以少量**真实机器抽样**，降低「装不上 / 打不开」的未知风险。

| 思路 | 做法 | 适合验证什么 | 局限 |
|------|------|----------------|------|
| **虚拟机 + 快照** | 建一台仅装系统的 Win10/11 客户机，**安装前打快照**；测完卸载或**直接恢复快照**，等同「又来一台新电脑」。 | NSIS/portable、快捷方式、卸载、无 Python/无 Node 分支、防火墙与端口 | 与真机仍有驱动/性能差异；MuMu 全链路见下文嵌套虚拟化 |
| **云主机按小时** | Azure / 其它云厂商的 **Windows 桌面或 Server** 实例，用毕即删。 | 偶尔做「完全干净」全量安装回归；不占用本机磁盘 | 有费用；同样不是用户家里的硬件 |
| **本机「重置」或双系统** | **重置此电脑（保留文件或清空）**；或单独一块硬盘/分区只装「测试用 Windows」。 | 最接近真实硬件的安装体验 | 费时、打断工作；重置前务必备份 |
| **借一台** | 同事/家人的闲置笔记本，测完卸载。 | 真实驱动与杀毒环境 | 不可自动化、依赖人情 |

**不建议当作主测试手段的**：**Windows 沙盒（Sandbox）**——每次重启都是干净环境，但生命周期短、资源与场景受限，更适合验**单个可疑 exe**，不适合长期验证「Electron + 后端 + 模拟器」整套用户路径。

**与「不敢保证纯新电脑能跑」的关系**：行业上也没有团队能**数学上保证**所有配置；可行策略是 **(1) 干净 VM/云机覆盖安装与首次启动**，**(2) 文档写清系统要求与已知限制**，**(3) 发版前在 1～2 台「未装过本软件」的环境上抽样**（含 VM 即可覆盖很大一部分「首次安装」类 bug）。本文后续章节中的 Hyper-V、检查点、MuMu 注意事项，都是在落实第 (1) 条。

## 1. 结论摘要

| 目标 | 是否适合用 Windows VM | 说明 |
|------|----------------------|------|
| **NSIS / portable 安装包、首次启动、卸载、路径与权限** | **适合** | 与物理机行为高度一致；配合快照可反复「干净系统」验证。 |
| **Electron 壳 + 后端服务联调（无模拟器）** | **适合** | 一般仅需足够 CPU/RAM；注意 VM 显示与网络即可。 |
| **含 MuMu 模拟器 + ADB 的端到端自动化** | **可行但门槛高** | 需在 VM 内开启**嵌套虚拟化**，分配足够资源；部分机型/宿主组合下性能或兼容性不如物理机。 |
| **GPU 重度、低延迟游戏画面** | **不推荐单独依赖 VM** | 无 GPU 直通时帧率与图像栈差异大；更适合作为**安装/冒烟**，完整战斗表现仍以物理机为准。 |

**一句话**：用 Windows VM 做**安装与向导类测试**非常合适；做**全链路（含 MuMu）**需要额外配置嵌套虚拟化并接受性能与风险，与物理机互补而非替代。

## 2. 场景分工（建议谁测什么）

### 2.1 适合放在 VM 里测的内容（优先）

- **安装器行为**：`electron-builder` 产出的 NSIS、解压目录、快捷方式、卸载项。
- **「像用户一样」的路径**：非开发目录、含空格路径、非管理员账户。
- **依赖探测**：本机无 Python、无 Node 的发行版路径（见仓库 `docs/AutoScriptor/release-build-and-run.md`）。
- **首次运行**：生成配置、防火墙提示、端口占用等（需在 VM 网络策略下观察）。
- **回归**：同一镜像打快照 → 安装 A 版本 → 卸载 → 再装 B 版本。

### 2.2 建议仍在物理机或专用环境测的内容

- **MuMu 多版本路径**（`nx_main` / `shell`）与 **ADB 设备枚举** 的长期稳定性。
- **OCR / 截图 / 高帧率操作** 等对延迟敏感的能力。
- **Nuitka 大构建**：VM 磁盘与 CPU 往往弱于开发机；可 VM 测安装包，**构建仍在 CI 或主力机**。

### 2.3 交叉验证（VM + 物理机各测一层）

| 层级 | VM | 物理机 |
|------|----|--------|
| 安装/卸载/升级 | 主战场 | 抽样 |
| 后端启动与健康检查 | 主战场 | 抽样 |
| MuMu + 任务脚本 | 冒烟/可行性 | 主战场 |

## 3. 许可与系统镜像（避免法律与过期风险）

以下为常见做法，**具体条款以微软与贵司合规为准**：

- **Windows 11/10 零售许可**：若你有合法授权，部分场景可将同一许可用于 VM（取决于版本与「设备」定义）；企业环境常用 **VL + KMS** 或 **MDT 测试机**。
- **评估镜像**：微软 **Evaluation Center** 提供 Windows Server 等评估版（常见 **180 天**），适合短期干净环境；到期需重建或转正许可。
- **开发者向 VM**：微软曾提供预装开发工具的虚拟机镜像（Hyper-V、VMware、VirtualBox 等），可用自有密钥激活以去除试用限制（以当期下载页说明为准）。
- **不建议**：使用来源不明的「精简版 Ghost」作为测试基线，与真实用户环境差异过大。

**分工建议**：由**专人**维护 1～2 个「标准测试镜像」版本号与快照命名规范，避免每人各装一套导致无法复现问题。

## 4. 技术要点

### 4.1 Hyper-V（宿主为 Windows Pro/Enterprise）

- 宿主需 **Pro/企业版** 等才默认具备 Hyper-V 角色（家庭版需其他方案如 VMware Workstation Player 等，以当前微软文档为准）。
- **Windows 11 客户机**：建议使用 **第二代虚拟机**，并启用 **TPM、安全启动** 等以满足官方安装要求（微软社区与 TechTarget 等均有实践说明）。
- **检查点（Checkpoint）**：安装前建检查点，失败可回滚，适合重复跑安装测试。

### 4.2 嵌套虚拟化（VM 里再跑 MuMu / Android 类模拟器）

若必须在虚拟机内运行 **MuMu** 等依赖虚拟化扩展的组件：

- 在 Hyper-V 中对目标 VM 启用**向客户机暴露虚拟化扩展**（例如 PowerShell：`Set-VMProcessor -VMName <名称> -ExposeVirtualizationExtensions $true`）。官方概念与限制见 [What is Nested Virtualization?](https://learn.microsoft.com/virtualization/hyper-v-on-windows/user-guide/nested-virtualization) 与 [在虚拟机中启用嵌套虚拟化](https://learn.microsoft.com/windows-server/virtualization/hyper-v/enable-nested-virtualization)。
- 微软文档指出：**在 Hyper-V 虚拟机内**再跑**非微软且依赖硬件虚拟化扩展**的虚拟化软件**不在支持矩阵内、容易失败**；嵌套场景下对**延迟敏感**的应用也不推荐。实际能否跑 MuMu 取决于其引擎是否仍要求客户机暴露 VT/AMD-V，以及版本差异——**必须以实测为准**。
- 若宿主改用 **VMware Workstation / VirtualBox** 承载 Windows 客户机，内层再跑模拟器属于另一套「嵌套」组合，同样建议查**宿主厂商**与 MuMu 官方说明，避免与「物理机 + MuMu」结论混用。

**MuMu 与 Hyper-V**：公开资料表明 MuMu 新版本通过 **Nebula** 等路线改善与 **物理机**上 Hyper-V 的共存；**在「Hyper-V 虚拟机里的 Windows」再跑 MuMu** 属于更苛刻的叠加场景，仅适合**冒烟**，完整自动化仍以物理机为主。

### 4.3 资源与磁盘

- **RAM**：建议客户机 **8 GB 起**，跑 Electron + 模拟器时 **16 GB 更稳**。
- **磁盘**：固定大小 VHDX 可减少碎片与性能抖动；为安装测试预留 **≥60 GB** 较从容。
- **GPU**：无直通时依赖虚拟显卡，**不要**用 VM 内帧率对比物理机。

### 4.4 网络与隔离

- 测安装包时可**限制外网**或走代理，观察超时与重试；与测「在线更新」用的网络全开环境分开。

## 5. 与本项目（AutoScriptor）的对应关系

根据仓库 `README.md` 与 `docs/AutoScriptor/release-build-and-run.md`：

- **桌面端**：Electron + `npm`/构建流水线；发行用户侧为 **单文件 exe / NSIS**，后端为 **Nuitka 打包**，这些在 Windows VM 中验证安装路径与启动方式**很匹配**。
- **模拟器**：文档要求 **MuMu / MuMu12**；安装器中有 **MuMu 目录、`adb`、设备串号** 等校验（`services/installer/installer.py`）。在 VM 中验证时务必打开嵌套虚拟化并预留资源。
- **Python**：用户可能使用启动器在仓库内建 `.venv`；VM 中可模拟「无全局 Python」或「仅自带 `.python310`」等分支。

## 6. 推荐落地流程（可直接当 checklist）

1. **选宿主**：团队统一一种（如 Hyper-V 或 VMware），减少「在我机器能装」差异。
2. **基线镜像**：安装完系统 + 可选 Office/浏览器后打**干净快照**，命名为 `clean-YYYYMMDD`。
3. **安装测试**：从快照恢复 → 拷贝当日构建的 `installer.exe` / portable → 安装 → 记录日志与录屏。
4. **回滚**：卸载或恢复快照，重复下一构建号。
5. **MuMu 专项**：单独一个「重资源」快照；嵌套虚拟化开启后安装 MuMu，只做连接与简单启动冒烟，深度脚本仍物理机。
